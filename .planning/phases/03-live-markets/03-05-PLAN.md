<objective>
Deliver QA-03: the market-data test cases, executed, with the results recorded and every defect filed
— and fold what this phase learned into the test plan and the project's memory.

Purpose: the QA artifacts are this project's headline deliverable and the reviewer audience reads
them as evidence of how the engineer works, so two things are non-negotiable. The cases must attack
what is genuinely risky in this phase rather than restating the happy path: a formatter that is
correct for a five-figure coin and silently wrong for a sub-cent one, a sort that is not wrong so
much as undefined when a value is absent, a cache that is the only thing standing between this demo
and an exhausted API quota, a degraded mode that is either honest or dangerous depending on one
banner, and an API key in a public repository. And they must be run, not merely written — an
unexecuted case file does not satisfy the requirement (D-50, the same rule as D-33 in Phase 2).

This is also the phase boundary, so the two facts this phase actually settled — the real Demo rate
limits, which the risk register has been carrying as unconfirmed since Phase 1, and that the API
rejects the stablecoin ticker as a currency code — have to land in the risk register and the wiki
rather than living only in a research file.

Output: `qa/test-cases/markets.md`, an executed run report under `qa/runs/`, bug reports for any
failure, an updated test plan and QA README, a new wiki decision page with the concept and entity
pages brought up to date, and a one-line mirror in PROJECT.md.
</objective>

requirements covered and today's date; the usage notes; a short "Notes on the endpoints under test"

strings the cases assert verbatim; then the eight-column table. Ids run from `TC-MKT-001` upward and
are never reused. Priority follows the test plan's definitions; Type is exactly one of the five the

stays one row. Where a behavior also has an automated check, name the test file and test name, or the
smoke script section, inline in the Expected cell the way every auth row does, so the run report can

Every case names a concrete, checkable expected result — a status code and error code, a specific
rendered string, a specific ordering, a specific count — never "works correctly".

Cover at least these behaviors, one case each, with the requirement id in the Req column:

Table contents and formatting (MKT-01, DATA-04)
  1. The markets page lists exactly the curated number of pairs, each showing pair, price, 24h
     change, 24h volume and market cap.
  2. A logged-out visitor can open the markets page — no redirect to the login screen.
  3. Every pair renders against the stablecoin quote leg and the page states the convention that the
     underlying reference price is the dollar figure CoinGecko quotes.
  4. The stablecoin quote asset itself never appears as a tradable row — no self-pair.
  5. A five-figure price renders with two decimals and a thousands separator.
  6. A sub-cent price renders with enough significant digits to remain readable rather than
     collapsing to zeros — call out explicitly that this is the case a single fixed precision passes
     for major coins and fails for a real micro-cap.
  7. A negative 24h change renders with a minus sign and the down direction marker, a positive one
     with a plus sign and the up marker.
  8. Volume and market cap render abbreviated with a magnitude suffix.

Search (MKT-02)
  9. Typing part of a coin's name filters the table to matching rows.
  10. Typing part of a symbol in the opposite case to how it is displayed still matches.
  11. A query matching nothing shows an explicit no-matches message rather than an empty table.
  12. Clearing the search restores the full list.
  13. Typing produces no network request at all — the filter is client-side over the already-fetched
      payload. State the step as watching the network panel while typing.

Sort (MKT-03)
  14. Clicking price sorts descending, clicking again sorts ascending.
  15. Sorting by 24h change places the most negative value at one end and the most positive at the
      other, with correct handling of the sign.
  16. A row whose sorted value is absent appears last in both directions.
  17. Two rows with an identical sorted value keep a stable, repeatable relative order across
      repeated sorts.
  18. Sorting does not reset the active search, and a refresh landing mid-session does not reset the
      sort or the search.

Auto-refresh and freshness (MKT-05, DATA-02)
  19. The page refreshes itself on the stated interval while the tab is visible, with the
      last-updated line advancing.
  20. Switching to another tab stops the polling, and returning resumes it — state the observation
      method (the network panel while the tab is hidden).
  21. The last-updated line reports the age of the data the API returned, not the time of the local
      request.
  22. Several browser tabs open at once do not multiply upstream calls: the server-side cache
      collapses them. State the step as reading the upstream-call log lines, not as guessing.

Chart (MKT-04)
  23. Clicking a pair opens that pair's trade page and a chart is drawn for it.
  24. Switching between the three windows redraws the chart, with the number of drawn canvases
      staying at one — the leak check.
  25. Navigating away from the trade page and back does not leave a duplicate chart or a console
      error.
  26. The chart's plotted dates fall in the expected window rather than in an absurd future year —
      the millisecond-versus-second check, stated as reading the axis labels.

Degraded mode (DATA-03)
  27. With the upstream forced to fail through the local stub and the cache expired, the page shows
      cached prices with a prices-delayed banner naming the data's age; the table is still populated.
  28. The server log carries one stale-serve line for that request, carrying the same request id the
      response header returned and the upstream failure reason.
  29. Once the upstream recovers, the banner clears and fresh data returns.
  30. With the upstream failing and nothing cached at all, the page shows a clear failure with a
      request id rather than an empty table pretending to be data.

Attribution (MKT-05)
  31. The CoinGecko credit is visible on the markets page, on the trade page and in the shell footer,
      and the credit link opens CoinGecko.
  32. The chart library's own required attribution is visible on the trade page.

Security (DATA-01, DATA-04)
  33. The key-exposure case, which is success criterion 3 and the most important row in the file:
      with the network panel recording, walk the markets page, a search, a sort, a trade page and all
      three chart windows, then confirm that no request the browser made carries the key in a URL, a
      header or a body, and that no request was made to any CoinGecko host at all. State the steps
      precisely enough that a reviewer could repeat them, and state the pass condition as both of
      those things being true, not just the first.
  34. The built frontend bundle contains no occurrence of the key — a structural grep over the build
      output, complementing the traffic check.
  35. A chart request for a coin id that is not on the curated list returns the not-found error code,
      and the server log shows no upstream call for it.
  36. Running the API with no key configured still serves the markets page, at the lower keyless
      limit — the keyless-capable guarantee.

Mark the cases a reviewer would run first at the higher priority band; the exit criteria require all
of that band to be executed. Do not hardcode which coins are in the curated list in any case — the
list is dynamic by design, so cases pin whatever the list currently holds, or pin the stub's fixture.
Say so once in the preamble, because the later phases' cases inherit the same rule.

Extend the browser section 02-01 added so the run covers the whole journey D-34 asks for, keeping
the script's existing conventions: self-allocated free ports, a temporary database and log file,

Continue directly after 02-01's signup-and-reload assertions, in the same page and browser context
so the cookie jar is the real one:

1. Log out through the nav control that is present on every page, and wait for the nav to show the
   signed-out state.

2. Navigate to `/wallet` and assert the browser ends up on `/login` — the guarded route must not
   render wallet contents after logout. Assert on the resulting URL and on page content, so a guard
   that renders the login markup at the wrong URL still fails.

3. Log back in through `/login` with the same credentials used at signup, and assert the nav shows
   that email again and the wallet shows `10000.00000000`. This is the AUTH-02 login path proven in
   a real browser, and the same cookie round trip the manual cases will repeat by hand.

4. Assert that the session value is not readable from page JavaScript at any point after logging
   back in — the token lives only in an httpOnly cookie.

5. Query the temporary database read-only once more and assert the account still has exactly one
   USDT balance row worth `10000.00000000` after the whole journey. Signing in and out repeatedly
   must never re-credit an account.

6. Finish with the page-error and console-error assertion, naming this section in the failure
   message so a React error during login or logout fails the run rather than passing silently.

Leave every pre-existing check and its ordering alone; the health-badge poll-timing assertions
depend on running before the auth navigation.

2. Write `wiki/pages/decisions/session-auth-model.md` following `wiki/SCHEMA.md`'s page format —
   frontmatter with `title`, `type: decision`, `updated`, `sources` and `related` wiki-links, then

   length. It records, with the decision ids from `02-CONTEXT.md`:
   - Passwords hashed with the Node standard library's memory-hard key-derivation function, stored
     as a self-describing string that carries its own parameters, verified with a constant-time
     compare (D-14) — chosen over a native-addon alternative because the free-tier deploy in Phase 7
     must not need a build step, and reversible in one module.
   - Opaque 32-byte session tokens with only their hash stored server-side, so revocation on logout
     is a single delete and a leaked database row cannot be replayed (D-16); an httpOnly,
     `SameSite=Lax`, path-scoped cookie with a 7-day absolute lifetime and no sliding renewal (D-17,
     D-18, D-19).
   - Identity resolved only from the session cookie, with no endpoint in the phase accepting a user
     id from the client — the structural form of the cross-user isolation requirement, and why the
     isolation proof for this phase is a cookie swap rather than an object-reference attack (D-20,
     D-22). Note that phases adding id-bearing routes must add real object-reference cases then.
   - The 10,000 USDT grant written in the same database transaction as the account row, with the
     driver's synchronous-callback requirement called out as the trap that would silently break the
     guarantee, and the unique constraint as the backstop (D-24, D-25).
   - The deliberate asymmetry in error messages: generic on login to resist account enumeration,
     explicit on signup because the form already reveals existence (D-26) — recorded as an accepted
     trade-off, not an oversight.
   - The two wiring gaps this phase closed in existing Phase 1 code (the credentialed cross-origin
     contract on both sides, and the foreign-key pragma), and the test-scope choice made in 02-03:

   - The known gap: no login rate limiting in this phase, deferred to the hardening phase (D-31).

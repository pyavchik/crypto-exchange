<objective>
Expand the proven signup slice into the full account lifecycle on the server: log in, log out, read
your own wallet, and be told precisely what was wrong with bad input — without ever revealing which
email addresses exist and without ever accepting an identity from the client.

Purpose: AUTH-02, AUTH-03 and AUTH-04 are the requirements a QA reviewer will attack hardest, and
three of this phase's decisions are security trade-offs that only mean something if they are pinned
down by tests: the deliberately asymmetric error semantics (D-26), the cookie-scoped clear on logout
(D-18), and the structural claim that no endpoint in this phase can be given someone else's id
(D-20/D-22).

Output: `POST /api/login`, `POST /api/logout`, `GET /api/wallet`, per-field validation on the D-09
envelope, and the isolation / exactly-once / expiry proofs that back the QA cases in 02-05.
</objective>

<interface_contract>
This plan completes the HTTP surface declared in 02-01. The frontend plan 02-03 runs in the same
wave and codes against exactly these shapes — any deviation must be reflected in both plans.

| Method + path | Request | Success | Failure |
|---|---|---|---|
| `POST /api/login` | `{ email, password }` | `200 { email, balances: [{ asset, amount }] }` + `Set-Cookie: session=…` | `400 VALIDATION_ERROR` (+ `fields`), `401 INVALID_CREDENTIALS` |
| `POST /api/logout` | — | `200 { ok: true }`, cookie cleared | never fails (D-18) |
| `GET /api/wallet` | — | `200 { balances: [{ asset, amount }] }` | `401 UNAUTHENTICATED` |

Validation failure body (D-27), additive on the existing D-09 envelope:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Please fix the highlighted fields",
    "requestId": "…",
    "fields": { "email": "Enter a valid email address", "password": "Password must be at least 8 characters" }
  }
}
```

`fields` is present only on `VALIDATION_ERROR`; every other error keeps the three-member shape
unchanged. The code vocabulary is fixed by D-21 — `UNAUTHENTICATED`, `INVALID_CREDENTIALS`,
`EMAIL_TAKEN`, `VALIDATION_ERROR` — and every one of them travels in the D-09 envelope. Fixed user-facing strings the frontend and the QA cases both assert:

- Login failure (unknown email or wrong password, identical for both): `Invalid email or password`
- Duplicate signup: `That email is already registered`
- Invalid email: `Enter a valid email address`
- Short password: `Password must be at least 8 characters`
</interface_contract>

  <files>api/src/routes/auth.ts, api/src/routes/auth.test.ts, api/src/routes/wallet.ts, api/src/routes/wallet.test.ts, api/src/app.ts</files>
  <behavior>
    - `POST /api/login` with the credentials of an account created by signup returns 200, the account's email and balances, and a `session` cookie whose value differs from the signup cookie.
    - Both the signup cookie and the login cookie work on `GET /api/me` — logging in does not invalidate other sessions.
    - `POST /api/login` for an email that was never registered returns 401, code `INVALID_CREDENTIALS`, message `Invalid email or password`.
    - `POST /api/login` for a real email with the wrong password returns a byte-identical body except for `requestId`, and the same status and code.
    - `POST /api/login` matches the account case-insensitively: an address typed with different capitalisation and surrounding spaces logs into the same account.
    - `POST /api/logout` with a valid cookie returns 200 `{ ok: true }`, and the `session` cookie in the response is cleared with `path` `/`.
    - After logout, replaying the same cookie on `GET /api/me` returns 401 `UNAUTHENTICATED` — the session is dead server-side, not just gone from the browser.
    - `POST /api/logout` called a second time with the same dead cookie, and called with no cookie at all, both still return 200.
    - `GET /api/wallet` with a valid cookie returns exactly one USDT balance of `10000.00000000` for a fresh account.
    - `GET /api/wallet` with no cookie returns 401 `UNAUTHENTICATED` with a `requestId`.
  </behavior>
  <action>
1. `api/src/routes/auth.ts` — add two routes to the existing plugin, reusing the options it already
   receives (`accounts`, `sessions`, `requireSession`, `cookieSecure`) and the same
   `additionalProperties: false` response-schema discipline as the signup route.

   - `POST /api/login`: same body schema as signup. Normalize the email the same way signup does
     (`trim().toLowerCase()`), look the account up, and verify the password against the stored hash.
     When the account does not exist, still run a password verification against a throwaway hash
     before responding, so an unknown email and a wrong password take comparable time and the
     endpoint does not become an account-existence oracle by timing. Both failure modes throw the
     identical `AppError(401, "INVALID_CREDENTIALS", "Invalid email or password")` — one generic
     message, per D-26, because login is the surface an attacker enumerates. On success issue a
     fresh session, set the cookie and return 200 with `{ email, balances }`. A new token is minted
     on every successful login and no pre-authentication session concept exists, so there is nothing
     for a session-fixation attack to plant.

   - `POST /api/logout`: no `requireSession` preHandler — read the cookie directly, call
     `sessions.revoke(...)` when one is present, clear the cookie, and always return 200
     `{ ok: true }`. D-18 makes this idempotent: logging out with an already-invalid, already-used
     or entirely absent session is a success, not an error. Clear the cookie through the
     `clearSessionCookie` helper so the scoping options match the ones used when it was set — a
     mismatched path writes a second expired cookie and leaves the live one in the browser.

2. `api/src/routes/wallet.ts` (new) — a `FastifyPluginCallback<WalletRoutesOptions>` shaped like
   `health.ts`, taking `{ accounts, requireSession }`. One route, `GET /api/wallet`, registered with
   `{ preHandler: opts.requireSession }`. The handler reads `request.userId`, converts it back to a
   number, calls `accounts.listBalances(...)` and returns `{ balances }` under a response schema
   with `additionalProperties: false`. It must never read an identifier from the request path, query
   string or body — the session cookie is the only identity source in this phase (D-20), which is
   what makes AUTH-04 a structural property rather than a check that could be forgotten. Amounts are
   passed through as the stored decimal strings; nothing in this phase parses them as numbers.

3. `api/src/app.ts` — register the wallet routes alongside the auth routes, passing the same
   `accounts` service and the same `createRequireSession(sessions)` handler instance.

4. `api/src/routes/auth.test.ts` and `api/src/routes/wallet.test.ts` — cover every bullet in the
   behavior block. Build a small `signupAndLogin(app, email)` helper in the test file that returns
   the raw cookie value, and replay cookies with `app.inject({ ..., cookies: { session: token } })`.
   For the cookie-clearing assertion, read the `session` entry out of `response.cookies` and assert
   its `path` explicitly — asserting only that some `Set-Cookie` was sent would pass even for the
   broken mismatched-scope case. Write the failing test before each behavior.
  </action>

  <behavior>
    - Signing up with `"not-an-email"` returns 400, code `VALIDATION_ERROR`, and `error.fields.email` is `Enter a valid email address`.
    - Signing up with a 7-character password returns 400 and `error.fields.password` is `Password must be at least 8 characters`.
    - Signing up with an exactly 8-character password succeeds — the boundary is inclusive (D-15).
    - A password is never trimmed: a password of eight spaces plus a letter is accepted at its true length, and leading or trailing spaces are part of the secret at login.
    - Signing up with both fields invalid returns both members of `fields` in one response.
    - Signing up with an email that differs from an existing one only by capitalisation or surrounding whitespace returns 409 `EMAIL_TAKEN` with `That email is already registered`.
    - Logging in with an empty email returns 400 `VALIDATION_ERROR`, not 401 — malformed input is distinguishable from a failed credential check without revealing account existence.
    - An error thrown without a `fields` member still serialises to the exact three-member D-09 envelope, so every existing error response is unchanged.
    - A 500-class error still returns the generic internal-error envelope with no leaked message.
  </behavior>
  <action>
1. `api/src/lib/errors.ts` — two additive changes, nothing existing removed or reshaped.
   - Export an `AppError` class extending `Error` with `statusCode`, `code` and an optional
     `fields: Record<string, string>`. It replaces the cast-and-assign idiom currently repeated in
     `api/src/app.test.ts`; the existing `errorHandler` already turns any thrown error carrying
     `statusCode` and `code` into the D-09 envelope, so no handler rewiring is needed for the status
     or the code.
   - Widen `ApiErrorBody` with an optional `fields` member and give `errorBody` an optional fourth
     parameter. In `errorHandler`, attach `fields` to the body only when the thrown error actually
     carries a non-empty record and the status is below 500. Responses without field detail keep
     exactly the three-member shape they have today.

2. `api/src/routes/auth.ts` — add a shared `validateCredentials({ email, password })` helper used by
   both signup and login. It returns a `fields` record, and the route throws
   `new AppError(400, "VALIDATION_ERROR", "Please fix the highlighted fields", fields)` when that
   record is non-empty. Rules, per D-15 and D-27:
   - Email: trim, then require a non-empty value of at most 254 characters matching a single-`@`,
     dotted-domain pattern; failure message `Enter a valid email address`.
   - Password: never trimmed — the raw string is the secret. Require at least 8 characters; failure
     message `Password must be at least 8 characters`. Also reject anything longer than 200
     characters with the same field key and a length message, so an enormous input cannot be used to
     burn CPU in the key-derivation function.
   Both fields are validated in one pass so the frontend can highlight every problem at once rather
   than one per round trip.
   Keep the existing Fastify body schema in place: it rejects a missing key or a non-string value
   before the handler runs and already maps to `VALIDATION_ERROR` through the existing handler. The
   new helper covers semantic validity, which the schema cannot express per field.
   Convert the duplicate-email mapping added in 02-01 to throw `AppError` as well, so every
   client-facing failure in this module goes through one constructor.

3. `api/src/app.test.ts` — replace the inline cast-and-assign error idiom with `AppError` and add

  <files>api/src/lib/session.test.ts, api/src/lib/accounts.test.ts, api/src/lib/session.ts, api/src/lib/accounts.ts, api/src/routes/auth.test.ts, api/src/routes/wallet.test.ts</files>
  <behavior>
    - With two live accounts, each session cookie returns only its own account from `GET /api/me` and only its own balances from `GET /api/wallet` — user B's cookie never yields user A's data.
    - Swapping in a session token that was never issued returns 401, never another account's data.
    - A session is still valid one minute before its 7-day expiry and rejected one minute after, using an injected clock rather than a faked global timer.
    - Validating an expired session deletes its row, so the same token cannot be retried and the table does not accumulate dead rows.
    - Revoking a session removes exactly that row and leaves the same user's other sessions working.
    - Creating a second account with an email that already exists throws, and the `users` and `balances` tables still hold exactly one row each for that email.
    - Two signups for the same email fired back to back leave exactly one account and exactly one 10,000.00000000 USDT balance row.
    - Deleting a user row removes that user's sessions and balances, proving foreign-key enforcement is actually switched on.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /api/login` | Untrusted credentials cross here; the response is the primary account-enumeration surface |
| cookie jar → `GET /api/wallet` | The only channel that names whose balances are returned |
| browser → `POST /api/logout` | Session revocation; must be unforgeable in the direction that matters and harmless when replayed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-09 | Information Disclosure | `POST /api/login` responses | high | mitigate | One identical status, code and message for unknown-email and wrong-password (D-26); asserted byte-for-byte in Task 1 |
| T-02-10 | Information Disclosure | `POST /api/login` timing | medium | mitigate | A verification pass runs even when no account matches, so response time does not separate the two failure modes; the password compare itself is constant-time |
| T-02-11 | Spoofing | password brute force / credential stuffing | high | accept | D-31 defers rate limiting to Phase 6; scrypt's cost parameters slow each guess, and 02-05 records the gap in the test plan's risk register rather than leaving it undocumented |
| T-02-12 | Elevation of Privilege | `GET /api/wallet` | critical | mitigate | Session-only identity with no id accepted from path, query or body (D-20); cookie-swap and forged-token cases in Task 3 |
| T-02-13 | Spoofing | session lifetime | medium | mitigate | 7-day absolute expiry with no sliding renewal, checked on every read and the row deleted when stale (D-17, D-19) |
| T-02-14 | Spoofing | logout | high | mitigate | The session row is deleted server-side, so a copied cookie is dead after logout; the cookie is cleared at the exact scope it was set (D-18) |
| T-02-15 | Tampering | cross-site request forgery on the state-changing routes | medium | mitigate | `SameSite=Lax` withholds the cookie on cross-site subrequests, which covers the cross-site form and fetch vector for these JSON endpoints without a separate token scheme |
| T-02-16 | Denial of Service | key derivation on oversized passwords | low | mitigate | Passwords longer than 200 characters are rejected during validation, before any hashing work |
</threat_model>

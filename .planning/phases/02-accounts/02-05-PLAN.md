  <action>
D-32 fixes the shape of this file: the project template, `TC-AUTH-NNN` identifiers, a Req column
tracing every row to an AUTH requirement, and coverage spanning positive, negative, boundary and
security/isolation paths plus the exactly-once grant.

Create `qa/test-cases/auth.md` from `qa/templates/test-case-template.md`, keeping the template's
header block, usage notes and the exact eight-column table header. Fill the header block with the
feature name, area code AUTH, the requirements covered, and today's date. Ids run `TC-AUTH-001`
upward and are never reused. Priority follows the test plan's definitions; Type is one of the five
values the template allows. Multi-step cases separate steps with the line-break tag the template
specifies so each case stays one table row.

Every case names a concrete, checkable expected result — a status code and error code, a specific
message, a specific balance string, or a specific destination — never "works correctly". Where the
expected result is a message the API returns, quote it exactly as implemented so the case fails if
the wording drifts.

Cover at least these behaviors, one case each, with the requirement id in the Req column:

Positive (AUTH-01, AUTH-02, AUTH-03, AUTH-05)
  1. Sign up with a valid new email and an eight-plus character password; account is created and the
     user lands signed in.
  2. A brand-new account holds exactly 10,000.00000000 USDT and nothing else.
  3. Log in with correct credentials for an existing account.
  4. The session survives a full browser refresh with no re-login.
  5. Log out from a page that is not the wallet — the control is present in the shell on every page.

Negative (AUTH-01, AUTH-02)
  6. Sign up with a malformed email; the message appears under the email field and no account is
     created.
  7. Sign up with a seven-character password; the message appears under the password field.
  8. Sign up with an email that already exists; the explicit duplicate message is shown.
  9. Log in with an email that was never registered; the generic credential message is shown.
  10. Log in with a correct email and a wrong password; the message, status and error code are
      identical to the previous case — this pair is the account-enumeration check, and the case must
      state that the two responses have to match.
  11. Submit both fields empty; both field messages appear at once.

Boundary (AUTH-01, AUTH-02)
  12. A password of exactly eight characters is accepted.
  13. An email differing from an existing account only by capitalisation or surrounding spaces is
      treated as the same account.
  14. A session that has passed its seven-day lifetime is rejected — reachable by editing the
      session row's expiry in the database directly, which the case must spell out as its step.

Security and isolation (AUTH-02, AUTH-03, AUTH-04)
  15. The session cookie carries the http-only, same-site and path attributes the phase specifies,
      and a lifetime of seven days.
  16. The session value cannot be read from page scripts in the browser console.
  17. Visiting a protected page while signed out lands on the login screen.
  18. An unauthenticated API call to a session-scoped endpoint returns 401 with the phase's
      unauthenticated error code and a request id.
  19. Cookie swap: with two accounts signed in from two browser profiles or two API clients, each
      session returns only its own email and only its own balances.
  20. Replaying a copied session cookie after that session has been logged out returns 401 — logging
      out kills the session on the server, not only in the browser.
  21. Logging out twice in a row succeeds both times.
  22. Record the structural isolation observation: no endpoint in this phase accepts an account
      identifier from a path, query or body, so there is no id-parameterised route to attack; the
      case states this explicitly and notes that the phases adding such routes must add real
      object-reference cases then.

Exactly-once crediting (AUTH-05)
  23. Two rapid duplicate signups for the same email leave exactly one account and exactly one
      10,000.00000000 USDT balance row.
  24. Logging out and back in several times never changes the balance.

Mark the cases a reviewer would run first as the higher priority band; the exit criteria require all
of that band to be executed. Where a behavior is also covered by an automated check, put the test
file or command in the Preconditions or Steps cell so the run report can cite it as evidence rather
than pretending a seven-day wait happened by hand.

<task type="auto">
  <name>Task 2: Execute the cases and file the run report</name>
  <files>qa/runs/, qa/bugs/</files>
  <action>
Run the cases against the real application and record what actually happened. Do not mark a result
from reading the source — a result is what the running system did.

1. Record the build under test: `git rev-parse --short HEAD`, and the version and commit the health
   endpoint reports once the API is up. Confirm the entry criteria before starting: the local gate
   is green and `npm run smoke` passes on this commit.

2. Start the stack the way `scripts/smoke-dev.mjs` does, not on the default ports: allocate two free
   ports, then spawn `npm run dev` with `PORT`, `HOST`, `VITE_PORT`, `VITE_API_URL`, `CORS_ORIGIN`,
   `DATABASE_PATH`, `LOG_FILE` and `GIT_COMMIT` set to that temporary environment. The developer may
   have their own dev server running on the conventional ports — never bind them, and never kill a
   process this task did not start. Tear down only the spawned process group at the end.

3. Execute the browser-facing cases by driving installed Google Chrome through `playwright-core`
   with `channel: "chrome"`, the same mechanism the smoke script uses, since the bundled browser
   cannot be installed on this machine. Execute the API-facing cases with direct HTTP calls against
   the temporary API port, keeping each client's cookie jar separate so the cookie-swap case is a
   genuine two-session test. Use a fresh account per case where the case says so — the test plan
   requires fresh accounts rather than shared ones.

4. Capture evidence as you go: the status code and error code for API cases, the `X-Request-Id`
   header for any failure, and the matching structured log line from the temporary log file found by
   that request id. That request-id thread is the evidence workflow the test plan defines, and it is
   what a bug report needs to be actionable. Never record a session cookie value, a password or an
   API key in any artifact — this repository is public and browser-captured evidence is not redacted
   automatically.

5. Write the run report at `qa/runs/RUN-<today>-auth.md` using `date +%F` for the date, from
   `qa/templates/run-report-template.md`. Fill every field: run id, scope and phase, build commit,
   environment (the URLs actually used, the Chrome version, the OS version from `sw_vers`, and the
   API version from the health endpoint), tester, and dates. The summary counts must add up to the
   number of cases in the results table, and the results table must carry one row per case id in
   `qa/test-cases/auth.md` with an actual result — no unfilled template placeholders may remain.
   Check off only the exit criteria this run genuinely satisfies, and use the observations section
   for near-misses and environment quirks that are not filed defects.

6. For every failing case, file `qa/bugs/BUG-NNN-<slug>.md` from the bug report template, numbered
   after the highest existing bug, matching the field table and section structure of the existing
   filed bug exactly. Set severity from the test plan's definitions — a cross-user data leak or a
   wrong balance is the top band, and the project rule is that both of the top two severity bands
   are the top priority band. Link the case id and the requirement id, quote the request id and the
   log excerpt, and list the bug in the run report's bugs-raised section. If the root cause is
   non-trivial, add a wiki finding page and link it from the bug the way the existing one does.

7. If a top-severity defect is found, stop and report it in the SUMMARY rather than papering over it
   in the results table — the phase cannot close with one open, and the honest record is the point
   of the artifact.
  </action>

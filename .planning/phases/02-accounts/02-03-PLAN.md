<objective>
Complete the browser surface of the account lifecycle: a login screen, a Log out control that is
present on every page, route guards for the pages that hold private data, and inline field-level
error messages on both forms.

Purpose: AUTH-03 says "log out from any page", and AUTH-01's error cases are only real to a user if
the message appears next to the field that caused them. This plan also settles the one open
tooling question the research raised — whether to introduce a DOM test environment this phase — and
settles it explicitly rather than by accident.

Output: `/login`, `ProtectedRoute`, the nav auth controls, per-field inline errors on both forms,
and view-level tests for every visual state.
</objective>

<api_contract>
This plan runs in the same wave as 02-02, which implements the server side of these three calls.
Code against exactly these shapes; do not invent alternatives if an endpoint is not yet reachable
locally — the runtime proof is 02-04's real-browser run.

| Call | Request | Success | Failure |
|---|---|---|---|
| `POST /api/login` | `{ email, password }` | `200 { email, balances: [{ asset, amount }] }` + session cookie | `400 VALIDATION_ERROR` with `error.fields`, `401 INVALID_CREDENTIALS` |
| `POST /api/logout` | — | `200 { ok: true }`, cookie cleared | never fails |
| `GET /api/wallet` | — | `200 { balances: [{ asset, amount }] }` | `401 UNAUTHENTICATED` |

Validation failures carry an optional `fields` member on the existing D-09 error envelope:
`{ error: { code: "VALIDATION_ERROR", message, requestId, fields: { email?, password? } } }`.
Server-side messages the forms render verbatim: `Invalid email or password`,
`That email is already registered`, `Enter a valid email address`,
`Password must be at least 8 characters`.
</api_contract>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| page JavaScript → session cookie | The token must remain unreadable from the page; the frontend stores no session material of its own |
| API error bodies → rendered DOM | Server-supplied strings, including request ids and field messages, are rendered into the page |
| route guard → private pages | A client-side gate that improves the experience but is not the security control |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-17 | Information Disclosure | `web/src/lib/auth.tsx` | high | mitigate | No token, email or balance is written to browser storage; the httpOnly cookie is the only session store, so an XSS cannot read the session out of the page |
| T-02-18 | Tampering | error and field messages rendered in the forms | medium | mitigate | Server strings are rendered as React text children only, never as raw markup — the same rule the health badge already follows |
| T-02-19 | Elevation of Privilege | `ProtectedRoute` | medium | accept | The guard is a user-experience control, not a security boundary; every private read is authorised server-side by the session preHandler, and 02-02's tests prove the API rejects unauthenticated calls regardless of what the client renders |
| T-02-20 | Spoofing | Log out control | high | mitigate | Logging out calls the server revocation endpoint rather than merely clearing local state, so the session dies at the source; the local state is cleared even if that request fails |
</threat_model>

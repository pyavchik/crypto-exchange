<objective>
Deliver the phase's tracer slice: a visitor signs up in a real browser and lands on a funded wallet
showing 10,000.00000000 USDT, and stays signed in across a page reload.

This is one vertical slice wired through every layer the phase touches — SQLite schema, password
hashing, session issuing, cookie transport, CORS credentials, the React auth bootstrap, the signup
form and the wallet view — proven end-to-end by the real-browser `npm run smoke` step before any
expansion work (login, logout, validation, isolation) is layered on top.

It is split across three commits purely for context budget: Task 1 is the API half, Task 2 is the
browser half, Task 3 is the real-browser proof that the cookie actually crosses the
`localhost:5173` → `localhost:3000` boundary. The slice is not done until Task 3 is green.

Purpose: three verified defects-in-waiting sit directly on this path — CORS without
`credentials: true`, fetch without `credentials: 'include'`, and a missing
`PRAGMA foreign_keys = ON` — and every one of them passes an `app.inject()` test while failing in a
browser. Proving the slice in Chrome first means an architectural dead-end costs one commit, not ten.

Output: `users`/`sessions`/`balances` tables + migration, `password.ts`, `session.ts`,
`accounts.ts`, `POST /api/signup`, `GET /api/me`, the React `AuthProvider`, `/signup` and `/wallet`
pages, and an extended `npm run smoke` browser step.
</objective>

  <reversibility rating="costly">The stored password-hash encoding (D-14) and the opaque-token session model (D-16) are cheap to change before any real account exists, but a later swap to argon2id requires re-hashing on next login. The self-describing `scrypt$N$r$p$salt$hash` string is exactly the escape hatch that keeps that a one-module change.</reversibility>
  <behavior>
    - `hashPassword("correct horse battery staple")` then `verifyPassword` with the same string resolves true; with any other string resolves false.
    - Two `hashPassword` calls on the same password produce different stored strings (random per-user salt).
    - `verifyPassword("anything", "not-a-real-hash")` resolves false rather than throwing.
    - `verifyPassword` derives its key at the byte length of the stored hash, so a corrupted stored string rejects instead of throwing from the constant-time compare.
    - `POST /api/signup` with `{ email: "a@example.com", password: "password1" }` returns 201, body `{ email: "a@example.com", balances: [{ asset: "USDT", amount: "10000.00000000" }] }`.

    - Replaying that cookie on `GET /api/me` returns 200 with the same email and balances — the simulated browser refresh.
    - `GET /api/me` with no cookie, a garbage cookie, and a cookie whose session row was deleted each return 401 with `error.code === "UNAUTHENTICATED"` and a `requestId`.

6. `api/src/lib/password.ts` (new) — implement D-14 exactly per 02-RESEARCH.md Pattern 1:
   `promisify(scrypt)`, constants `N=16384`, `r=8`, `p=1`, key length 32, salt length 16, stored
   string `scrypt$N$r$p$saltHex$hashHex`, verification through `timingSafeEqual`. Two rules the
   research calls out and the tests below pin down: derive the candidate key at
   `expected.length` (never a hardcoded length) because the constant-time compare throws on a byte
   length mismatch instead of returning false; and return false for any stored string that does not
   split into six `scrypt`-prefixed parts. Leave a short comment at the constant declarations noting
   that Node errors when `128 * N * r` exceeds the 32 MiB default memory bound — the chosen
   parameters need 16 MiB, so raising N later is the thing that would start throwing. Named exports
   only, a doc comment citing D-14, and nothing in this module ever logs a password or a derived key.

7. `api/src/lib/session.ts` (new) — implements D-16/D-17/D-19/D-20. Export `SESSION_COOKIE_NAME`
   (`"session"`) and `SESSION_TTL_MS` (7 days in ms). `generateSessionToken()` returns 32 random
   bytes base64url-encoded; `hashSessionToken(raw)` returns its SHA-256 hex. `createSessionService`
   follows the `createCoingeckoStatusService` factory shape — closes over an injectable `db` and
   `now = Date.now` so expiry tests can inject a clock instead of faking global timers.
   - `create(userId)` inserts `{ tokenHash, userId, createdAt, expiresAt }` and returns the raw
     token plus `expiresAt`. Only the hash is ever persisted, so a leaked database row cannot be
     replayed as a session.
   - `validate(rawToken)` looks the row up by hash; if `Date.parse(row.expiresAt) <= now()` it
     deletes that row and returns null (D-19's lazy expiry — there is no background sweeper this
     phase); otherwise returns `{ userId }`.
   - `revoke(rawToken)` deletes the row by hash and is a no-op when nothing matches.
   Every method is synchronous — better-sqlite3 is a synchronous driver, and keeping these methods
   synchronous is what makes the atomic write in step 8 safe.
   Also export `setSessionCookie(reply, rawToken, secure)` and `clearSessionCookie(reply, secure)`.
   Both pass the identical option set — `path: "/"`, `httpOnly: true`, `sameSite: "lax"`, `secure` —
   and the setter adds `maxAge: SESSION_TTL_MS / 1000` (the plugin's unit is seconds). The clearing
   helper must repeat the same scoping options: a cookie is identified by name plus path, so
   clearing with a different path creates a second expired cookie and leaves the live one in the
   browser, which would make logout appear to succeed while the browser stays signed in.
   Finally export `createRequireSession(sessions)`, returning an async Fastify `preHandler` that
   reads `request.cookies[SESSION_COOKIE_NAME]`, calls `validate`, and on failure replies 401 with
   `errorBody("UNAUTHENTICATED", "Not signed in", request.id)` and returns the reply to
   short-circuit — that status and code are D-21's contract for an unauthenticated request, carried
   in the existing D-09 envelope. On success it assigns `request.userId = String(session.userId)`. The `String(...)`
   conversion is required: `api/src/app.ts` already declares `FastifyRequest.userId` as
   `string | null` and `RequestLogController` already reads it into every request-completed log
   line, so the identity lands in the logs for free. Do not widen that declared type.

8. `api/src/lib/accounts.ts` (new) — same factory shape, injectable `db` and `now`.
   `STARTING_USDT = "10000.00000000"`.
   - `createWithGrant({ email, passwordHash })` wraps both inserts in one `db.transaction(...)`
     call whose callback is a plain, non-async function: insert the `users` row with
     `.returning().get()`, then insert the `balances` row (`asset: "USDT"`,
     `amount: STARTING_USDT`) with `.run()`, and return the user. This is D-25's exactly-once
     guarantee and the single highest-risk detail in the phase — better-sqlite3 returns from the
     transaction as soon as the callback returns, so a callback that yields to the event loop
     commits before its statements run, silently writing the balance outside the transaction. Every
     statement inside the callback must execute synchronously, and the callback must not await
     anything. Hash the password before calling this function, never inside it. Do not write an
     illustrative counter-example in a comment — the verification gate greps this file for the
     forbidden construct.
   - `findByEmail(email)` and `listBalances(userId)` are plain synchronous reads.
   Email normalization (`trim().toLowerCase()`) happens in the route before any call here, so the
   unique index compares normalized values only (D-23).
   The duplicate-email case surfaces as a better-sqlite3 unique-constraint error thrown out of the

## Environment setup

A dedicated temporary instance was started the way `scripts/smoke-dev.mjs` does, never on the
developer's conventional ports: two free ports were allocated (`58611` API, `58612` web) and
`npm run dev` was spawned with `PORT`, `HOST`, `VITE_PORT`, `VITE_API_URL`, `CORS_ORIGIN`,
`DATABASE_PATH`, `LOG_FILE=.../auth-qa.log` and `GIT_COMMIT=a229ad9` pointed at a scratch SQLite
file and log file outside the repo. Entry criteria were confirmed on commit `a229ad9` before any
case ran: `npm run lint`, `npm run typecheck`, `npm test` (87 API + 70 web, all passing) and
`npm run smoke` (`SMOKE OK`) were all green. The spawned process group was the only thing torn
down at the end of the run; no process the run did not start was touched.

Browser-facing cases were driven with installed Google Chrome via `playwright-core`
(`channel: "chrome"`, headless), the same mechanism `npm run smoke` uses (the bundled Chromium
cannot be installed on this machine, macOS 13). API-facing cases were driven with direct HTTP
calls (`curl` and small Node scripts using `fetch`), keeping every "client"'s cookie in an
independent variable so the cookie-swap case (TC-AUTH-019) is a genuine two-session test — never
a shared cookie jar. TC-AUTH-014 (session expiry) edited the `sessions.expires_at` column
directly in the temp SQLite file, per the case's own precondition, then replayed the cookie
against the running server. Every account used a fresh, timestamp-suffixed email — no case
reused another case's account.

## Observations and Risks

- **CI status not confirmed for this exact SHA.** The local branch is ahead of `origin/main` and
  commit `a229ad9` has not been pushed, so GitHub Actions has not run against it yet. The full
  local gate that CI mirrors (`npm run lint`, `npm run typecheck`, `npm test`, `npm run smoke`)
  was confirmed green on this exact commit immediately before this run started — recorded above
  — but that is a strong local proxy, not a substitute for the actual CI run. Re-check this box
  once the branch is pushed and Actions has run.
- **Test-script bug, not an app defect:** the first pass of the API-execution helper script sent
  a `Content-Type: application/json` header on bodyless `POST /api/logout` calls, which Fastify's
  body parser correctly rejected with 400 `FST_ERR_CTP_EMPTY_JSON_BODY` before the handler ran.
  This was a defect in the QA harness (an unconditional header), not in the application under
  test; it was fixed (only set the header when a body is actually sent) and TC-AUTH-020/021/024
  were re-executed and passed. Documented here rather than as a filed bug, since the running
  application's own behavior was correct throughout — Fastify rejecting a malformed request is
  the expected behavior of the server, and no `qa/bugs/` entry describes this class of failure.
- **TC-AUTH-008's written expectation was corrected during execution**, not the app: the case
  originally said the duplicate-email message renders as a "form-level error"; the app actually
  renders it under the email field specifically (`EMAIL_TAKEN` → `fieldErrors.email`, per
  `web/src/lib/auth.tsx`). `qa/test-cases/auth.md` was updated in place to describe the real
  behavior; this is a documentation fix to the test case, not a product defect — the status,
  code, and message text were all correct as designed.
- No login rate limiting exists yet (D-31) — no case in this file exercises it, and none should
  until the hardening phase implements it; see the new risk row this plan adds to
  `qa/TEST-PLAN.md`.
- The login/signup error-message asymmetry (D-26) is intentional and was specifically asserted by
  TC-AUTH-009/010 (identical failure for both cases) versus TC-AUTH-008 (explicit duplicate-email
  message) — behaving exactly as designed, not an inconsistency.

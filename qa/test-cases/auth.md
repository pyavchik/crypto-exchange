## Usage Notes

- One file per feature, stored at `qa/test-cases/<FEATURE>.md`.
- IDs follow `TC-AREA-NNN` (e.g. `TC-AUTH-001`) and are never reused, even if a test case is retired.
- Priority is P1, P2, or P3 (see `qa/TEST-PLAN.md` Priority section).
- Type is exactly one of: `positive`, `negative`, `boundary`, `security`, `UX`.
- For multi-step cases, separate steps inside the Steps cell with `<br>` (HTML line-break) tags so the table stays one row per test case.

## Notes on the endpoints under test

`POST /api/signup`, `POST /api/login`, `POST /api/logout`, `GET /api/me`, `GET /api/wallet` — all
error responses use the shared envelope `{ error: { code, message, requestId, fields? } }`. Fixed
user-facing strings this file asserts verbatim (per `.planning/phases/02-accounts/02-02-SUMMARY.md`'s
interface contract): `Invalid email or password` (401 `INVALID_CREDENTIALS`), `That email is already
registered` (409 `EMAIL_TAKEN`), `Enter a valid email address` (400 `VALIDATION_ERROR`, field
`email`), `Password must be at least 8 characters` (400 `VALIDATION_ERROR`, field `password`), `Not
signed in` (401 `UNAUTHENTICATED`). A fresh signup returns `{ email, balances: [{ asset: "USDT",
amount: "10000.00000000" }] }`. Automated analogs already exist in `api/src/routes/auth.test.ts`,
`api/src/routes/wallet.test.ts`, `api/src/lib/session.test.ts`, `api/src/lib/accounts.test.ts`, and
`scripts/smoke-dev.mjs` sections (k)-(q) — cited per case below where they cover the same behavior,
so the run report can point at that automated proof as corroborating evidence rather than re-deriving
it from a fresh manual pass alone.
